# Load test: 2000-item Space (2026-11-25)

How the UI-free core holds up with a Space big enough to feel: 1000 notes
(parent chains up to depth 6, 60 folders, tags, statuses including words
outside the fixed set, priorities), 600 tasks (a third under a parent, board
statuses, priorities, due dates) and 400 events (a quarter under a parent,
half with a `TZID`, half floating).

The script is `tool/load_test.dart`:

```
dart run tool/load_test.dart
```

It is a plain script (not a test) and touches no network: the CalDAV side is
the in-memory `FakeCalDav` from `test/support`. Built with the Dart 3.14 JIT
(`dart run`), one run, desktop x86-64. Anything over 50 ms is counted as slow.

## Results

| step | ms | note |
|---|---:|---|
| build the 2000 items (setup) | 92.8 | includes JIT warm-up |
| core parse: 1000 notes | 55.8 | 337 KiB |
| core parse: 600 tasks | 18.6 | 145 KiB |
| core parse: 400 events | 14.8 | 103 KiB |
| `NoteTree.build`: 1000 notes | 7.9 | 840 nested |
| `NoteTree.descendants`: one subtree | 0.3 | |
| `ItemService.list`: 500 of 2000 | 339.0 | parses all three kinds |
| `ItemService.board()` | 96.9 | notes only, 1000 |
| `ItemService.list(under: a folder)` | 119.6 | scope filter |
| scope walk: every task and event under one folder | 0.4 | 1000 walks, mirror of the app |
| `ProjectIndex` build (parent chains, 2000 items) | 2.1 | |
| `ProjectIndex.statsOf` every project | 5.4 | |
| sync: first pull of 1000 notes | 97.5 | no local copies yet |
| sync: merge 1000 against a modified copy | 319.2 | pulls, merges, pushes 1000 |

Slow (over 50 ms): 1000-note parse, `ItemService.list`, `board()`,
`list(under:)`, the first pull and the merge sync. The setup row is the JIT
warm-up, not data building.

## Where it gets slow

**Parsing dominates.** Reading one big calendar text of 1000 notes costs
55.8 ms, about 56 µs per note, against 31 µs per task and 37 µs per event.
The tasks and events are smaller but the note bodies carry header lines plus
prose; `parseNotes` runs one `split('\n')` per resource plus property
unfolding. At 2000 items a full read is a fifth of a second before anything
is filtered or sorted.

**`ItemService` has no cache.** `_load()` issues three REPORTs and parses
everything on every call, so `list()` costs the whole read even when it
returns 500 rows (339 ms: parse of all 2000 plus the sort). `board()` calls
`list()` again internally (96.9 ms for the 1000 notes), and
`list(under: ...)` builds a `NoteTree` over every item to find one subtree
(119.6 ms). Two board refreshes in a row pay twice.

**The parent-chain walks are cheap.** The app-side scope filter (mirrored in
the script, 1000 bounded walks up the parent links) takes 0.4 ms because the
trees and uid maps are already built; `ProjectIndex`, which walks chains
across notes, tasks and events and memoises them, takes 2.1 ms to build and
5.4 ms for every project's counts. Chain walking is not the problem; the
repeated parse per call is.

**Sync is linear and pays for the merge.** A first pull of 1000 notes is
97.5 ms (REPORT, parse, store writes). Merging the whole set against a
modified copy — local summary edited, remote body edited, then pull, merge,
push 1000 — is 319.2 ms, roughly 0.3 ms per item across the three-field
merge plus the PUT round trip through the in-memory server. Real latency to
a CalDAV server would be far worse: the push is serial.

## What would help, in order

1. A parsed load cache in `ItemService` (one `_load` shared by `list`,
   `board`, `overview` and the single-item reads), invalidated on write.
2. `board()` reusing the caller's notes list instead of listing again.
3. `list(under:)` building the tree only from the kind's parents, or a uid
   index, instead of a `NoteTree` over all items.
4. Batch the sync push (several PUTs in flight) if a server tolerates it.

Nothing here is a correctness problem; the numbers are the cost of "read
everything, parse it, then filter", which is fine for a few hundred items
and starts to show at 2000.
